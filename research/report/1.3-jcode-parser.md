# Task 1.5: Jcode Session Parser

**Agent**: Reasonix | **Status**: ✅ | **Time**: ~1h 20min

## What Was Done

Implemented `JcodeSessionParser` (implements `AgentSessionParser` for `AgentType::Jcode`) in `cacm-core`, registered it plus four Phase-2 stub parsers in the default `ParserRegistry`, and added a 17-test integration suite.

On-disk format (verified against the current jcode source in this workspace, `jcode/crates/jcode-base/src/session/`):

- `~/.jcode/sessions/<session_id>.json` — full snapshot (`id`, `created_at`, `status`, `messages`, ...)
- `~/.jcode/sessions/<session_id>.journal.jsonl` — append-only journal; each line is `{meta, append_messages: [StoredMessage...]}`

Parser behavior:

- **`parse_session_manifest(path)`** — accepts a snapshot file, a journal file (id from stem, status/timestamp from the last entry), or a directory containing exactly one snapshot. Maps jcode `SessionStatus` (string or `{"Crashed":...}` object forms) → cacm `SessionStatus` (`closed`→`completed`, `crashed|error|rate limited`→`failed`, rest→`active`).
- **`parse_turn(raw)`** — parses one JSONL line into an `AgentTurn`. Accepts both a `StoredMessage` line (`role`, `content`, `timestamp`) and a journal-entry line (`meta` + `append_messages`, combined into one turn). Extracts user text / assistant text from `text` blocks, tool calls from `tool_use` blocks, and file modifications from file-edit tool inputs (`edit`/`write`→Modify, `delete`/`rm`→Delete, `rename`/`move_file`→Rename, with Claude-Code-style alias + `functions.` prefix normalization mirroring `jcode_tool_types::resolve_tool_name`).
- **`detect_activity(path)`** — true for existing `.json` snapshots and `.journal.jsonl` files.

Stub parsers (`claude.rs`, `codex.rs`, `opencode.rs`, `cursor.rs`) implement the trait but return the new `ParseError::NotImplemented` from every parsing method.

## Key Decisions

- **Flat-file layout is the truth, not `research/06-jcode-internals.md`.** The research doc claims `sessions/<id>/transcript.jsonl` + `state.json`, but the current jcode source (`jcode-base/src/session/storage_paths.rs`: `session_path_in_dir` = `sessions/{id}.json`, `session_journal_path_from_snapshot` = `{stem}.journal.jsonl`) writes the flat layout. The parser follows the source and is flexible enough for both (snapshot file / journal file / directory).
- **`parse_turn` sets `turn_index: 0`** — it has no positional context; the watcher/daemon assigns real indexes when sequencing. Documented on the method.
- **File modifications come from `tool_use` inputs, not `tool_result` bodies.** jcode `tool_result` blocks carry only `tool_use_id` + plain text — structured file paths live in the matching `tool_use` `input` (`file_path` / `path` / `file`). `write` maps to Modify (creation cannot be distinguished without existence checks).
- **Defensive parsing for real-world files**: unknown content-block types fall to `#[serde(other)] Unknown`; unknown roles (`system`, `developer`, ...) fall to `Role::Other` (custom deserializer — `#[serde(other)]` is unavailable on externally-tagged enums); known-but-unconsumed block variants and `tool_result.content` are lenient (`#[serde(default)]`, untyped `Value`) so Anthropic-wire shapes never kill a whole line. Only `Text`/`ToolUse` are consumed, and those stay strict.
- **`ParserRegistry::new()` stays empty** (existing unit tests assert it); the default set lives in the new `ParserRegistry::with_defaults()`. The daemon still constructs `ParserRegistry::new()` — wiring `with_defaults()` there is a follow-up (daemon never calls parser methods yet).
- **Journal manifest semantics**: append-order is authoritative for status (last parseable entry wins); `created_at` (absent from journals) falls back to the newest `updated_at` seen; turn timestamp uses the newest appended message.
