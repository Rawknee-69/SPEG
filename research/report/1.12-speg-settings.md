## What Was Done

T3 Code's `/settings` route now has a **SPEG** category — a client-local settings panel for the SPEG integration: jcode binary/build config, the cacm-daemon connection, context injection, per-agent watching, and Phase-3 skill toggles. ## Panel behavior

- **Jcode**: binary path mode select (Auto-detect / Manual; the manual-only path input appears only in manual mode), optional build command, launch args.
- **CACM daemon**: host + port (port validated 1..65535, defaults to the `@cacm/sdk` `ws://localhost:9786`), auto-start switch, storage backend select (SQLite / Sled / In-memory), watch paths editor (one path per line, parsed/trimmed on blur).
- **Context injection**: mode select (Auto / Manual / Off) and max context budget in tokens (non-negative integer, default 8 000).
- **Agent watching**: one switch per `AgentType` (Jcode, Claude Code, Codex, OpenCode, Cursor, SPEG), persisted in the `watchedAgents` record.
- **Skills**: Phase-3 placeholder row when no skills are registered; registered skills render as toggles from the `skillToggles` blob.
- Every control commits immediately through `useUpdateClientSettings` (localStorage-backed `ClientSettings.speg`) — no save button, matching the rest of the settings UI. Text fields keep a local draft and commit on blur/Enter so keystrokes don't spam persistence.

## Decisions (deviations from the letter of the task, all reversible)

- **Settings schema added to `ClientSettings` (contracts), not a new storage layer**: "save persists" is the client-settings localStorage path (`localApi.persistence`), and the decode would strip any key absent from `ClientSettingsSchema`. The `speg` blob is whole-object replacement in the patch — the same convention as `providerModelPreferences`/`sidebarProjectGroupingOverrides` (an all-optional nested patch would not be assignable to the full type in `useSettings.ts`'s snapshot+patch spread).
- **Test lives in `apps/web/src/components/speg/`, not `apps/web/test/`**: same rationale as 1.11 — the web unit project's include glob is `src/**/*.test.{ts,tsx}` (`apps/web/vite.config.ts`), so `apps/web/test/...` would never run under `vp test run --project unit`.
- **Registration happens in `settingsSearch.ts` + `SettingsSidebarNav.tsx` + a new route file, not in `routes/settings.tsx`**: the task's "UPDATE settings.tsx" is a template artifact — in this codebase `settings.tsx` is only the layout shell; categories are registered via the `SettingsPath` union, `SETTINGS_SECTION_LABELS`, the sidebar icon map, and a file-based route. Followed the real pattern (the RESEARCH section asked for exactly this).
- **`packages/contracts/src/speg/spegSettings.ts` lives in the speg contracts folder and is re-exported from `@t3tools/contracts/settings`** (not the root barrel — task 1.15 still pending). The speg barrel export was added so 1.15 picks it up automatically.
- **Schema validation is strict** (closed `watchedAgents` record, port 1..65535, non-negative budget): invalid persisted values reject the blob rather than silently defaulting — appropriate for a brand-new key with no legacy data.
