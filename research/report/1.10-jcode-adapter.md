## Architecture

```
T3 Code provider registry (BUILT_IN_DRIVERS)
 └─ JcodeDriver.create()  (per provider instance)
     ├─ JcodeProcessManager ── JcodeClient.launch({binary?, jcodeHome?, inheritLogins}) ── private Rust daemon
     │      • spawn on first use (settings.binaryPath → SDK-bundled runtime → `jcode` on PATH)
     │      • ping() health probe with one transparent relaunch
     │      • auto-restart on unexpected transport close (bounded backoff via Effect runFork)
     │      • close() tears the daemon down (ephemeral home removed)
     ├─ JcodeAdapter (clientSource = manager.getClient)
     │      • one jcode session per thread (createSession / attachSession resume)
     │      • event pump over client.events(sessionId) → canonical ProviderRuntimeEvent
     │      • sendTurn (sendMessage), interrupt (cancel), respondToRequest (respondToPermission),
     │        stopSession, readThread (getHistory), rollbackThread (rewind), stopAll
     └─ JcodeTextGeneration (same manager) — throwaway session + runStructured + clear
```

**Event translation matrix** (implemented in `handleJcodeEvent`): `text_delta`→content.delta (assistant_text), `reasoning_delta`→content.delta (reasoning_text), `tool_start`→item.started, `tool_input_delta`/`tool_exec`→item.updated, `tool_done`→item.completed (call_id surfaced as `providerRefs.providerItemId`), `permission_request`→request.opened (bash→command_execution_approval, edit/write→file_change_approval, read→file_read_approval, else dynamic_tool_call), `token_usage`→thread.token-usage.updated, `turn_done`→turn.completed, harness `error`→runtime.error, `session_status`→session.state.changed, `session_renamed`→thread.metadata.updated, `background_progress`→task.progress. Unknown future event kinds are ignored (protocol v1 forward-compat).

**Resume**: `startSession` with a `{schemaVersion:1, sessionId}` cursor attaches the existing jcode session (`attachSession`); an `unknown_session` harness error falls back to creating a fresh session — so a daemon restart (or the manager's auto-restart) loses no thread continuity when `jcodeHome` is persistent.

## Decisions

- **Reused `@1jehuang/jcode-sdk` instead of writing a new client** — it is already a workspace dep (`speg/package.json`), ESM-only, Node ≥ 20, and mirrors `crates/jcode-harness-api` with schema-parity CI. The "JcodeProcessManager" is a thin lifecycle wrapper over `JcodeClient.launch`, not a hand-rolled NDJSON client (per the "copy what's locally available" working rule).
- **One private daemon per provider instance** (`launch()` embed mode), matching the `ProviderDriver` invariant that two instances share no mutable state; a persistent `jcodeHome` keeps transcripts across restarts.
- **Model inventory via the live daemon** in the snapshot probe (`listModels` on a throwaway session), cached 5 min so the periodic health refresh is cheap; falls back to `customModels`-only when the daemon is unreachable.
- **Windows credential-inheritance fallback**: `inheritLogins: true` symlinks the user's provider auth files into the instance home, which fails with `EPERM` on Windows without Developer Mode. The manager retries with `inheritLogins: false` (user can supply keys via `set_api_key`) — discovered and handled during verification.
- **Steering**: a `sendTurn` while a turn is active reuses the active turn id (jcode queues the prompt into the busy session), mirroring OpenCode/Claude behavior.

## Notes / Follow-ups

- **`JcodeClient.launch` needs an api-bridge-capable binary.** The 1.1.0 SDK's bundled win32 runtime lacks `api-bridge` (`error: unrecognized subcommand 'api-bridge'`); the fallback `inheritLogins:false` path reaches the same daemon-start step, so a full end-to-end turn on this machine requires the rebuilt local binary (`jcode/target/release/jcode.exe`) configured via `binaryPath`, or a newer SDK. This is a jcode packaging issue, not an adapter bug — the adapter's `launch()`/`ping()`/session path is exercised by the 21-test suite with the real SDK's client surface.
- **`respondToUserInput` is unsupported** — jcode's harness protocol v1 only raises permission prompts, so it returns a `ProviderAdapterRequestError` instead of hanging the orchestrator.
- **Attachments**: image attachments are read from `attachmentsDir` and passed as jcode base64 `ImageAttachment`s; text-generation ignores attachments (rarely needed for commit/branch/title prompts).
- **`maintenanceCapabilities` is manual-only** (`packageName: "@1jehuang/jcode-sdk"`, no update command) — jcode ships its own update path; version advisory enrichment was skipped to avoid an HttpClient dependency for now.
