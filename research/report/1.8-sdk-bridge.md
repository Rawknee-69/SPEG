## cacm-sdk-rs

`CacmClient` talks to the daemon's JSON-RPC-style WebSocket surface (`ws://127.0.0.1:9786/ws` default; `CACM_DAEMON_URL` override; bare `host:port` normalized):

- **Public API (all `async`)**: `connect(addr)`, `query(project, limit) -> Vec<CrossAgentContext>`, `sessions(project) -> Vec<AgentSession>`, `inject(session, agent) -> String`, plus `ping()`.
- **Connection**: one persistent `WebSocketStream` behind a `tokio::sync::Mutex`; opened lazily, reused, dropped on transport failure.
- **Request/reply correlation**: monotonic `id`; replies matched by id while server-initiated notifications (`{"event": ...}`) and other ids are skipped; daemon pings are answered with pongs.
- **Reconnect with exponential backoff**: transport/connect errors drop the socket and retry 100 ms → 10 s (×2), up to 8 attempts; JSON-RPC errors (`CacmError::Rpc`) and protocol errors are **not** retried. All public methods are idempotent reads, so retry is safe.
- **Errors**: `CacmError::{InvalidAddress, Connect, Transport, Timeout, Rpc, Protocol}` (hand-rolled, no extra deps).
- Re-exports `cacm_core::types` (`AgentType`, `ContextType`) for consumers.
- **Tests**: 7 unit tests run against an in-process mock daemon (`tokio-tungstenite::accept_async` + handler closure): query/sessions/inject roundtrips, notification-skipping correlation, RPC-error no-retry, reconnect-after-drop (server closes the first connection), address normalization. `cargo fmt`/`clippy` clean.

Deps: `tokio`, `tokio-tungstenite 0.24` (same major as the daemon's dev-dep), `futures-util`, `serde_json`, `serde`, `cacm-core` (path), `chrono` (dev).

## Daemon follow-up (from the 1.7 report)

`handle_inject` previously interpolated **raw** stored content into other agents' prompts with its own `format_inject`. It now routes through `cacm-core`'s `ContextInjector` (query → rank → format), which **sanitizes entry content** (line/control/Unicode-format chars) so crafted entries cannot break out of their bullet and inject instructions into `CLAUDE.md`/`.cursorrules`/prompts — the prompt-poisoning vector is closed server-side too. `agent`/`sessionId` flow from the RPC params (`AgentType::from_str`, unknown → Jcode). The `"*"` cross-project fallback stays (deliberate, task 1.4) but now passes through the sanitizer; the friendly empty-store placeholder is preserved. Old `format_inject`/`context_type_str` removed; handler tests updated to the per-agent format and a `inject_sanitizes_crafted_content` regression test added. ## jcode-cacm-bridge

Thin crate (~430 lines incl. tests, well under the task's "~200 lines" of real logic). Deps per spec: `cacm-sdk-rs` (path), `jcode-app-core`, `jcode-base`, `jcode-tool-core` (+ `jcode-tool-types`, `serde`, `serde_json`, `anyhow`, `async-trait`).

- **`CacmQueryTool`** (`cacm_query`) — params `{project, limit?}`; calls `CacmClient::query()`, returns entries as pretty JSON.
- **`CacmInjectTool`** (`cacm_inject`) — params `{session_id?, agent?}`; defaults session to the current tool-call session and agent to `"jcode"`; calls `CacmClient::inject()`, returns the formatted context text.
- **`register_cacm_tools(&Registry)`** — `async`; registers both tools via `Registry::register`.
- **`init_cacm_hook()`** — installs the turn-start hook (see below), idempotent.

### turn_start hook — the one deviation from the spec, user-approved

The spec said "registers turn*start hook via `jcode-base::hooks`". **Research finding: `jcode-base::hooks` has no programmatic registration API** — it is config-file/env-driven \_external commands* (observers/gates) dispatched from `jcode-app-core` (`agent/turn_execution.rs::fire_turn_start_hook`), and the turn boundary itself lives inside `jcode-app-core`/`jcode-tui`, which the vanilla constraint freezes. So `init_cacm_hook()` implements the bridge's **own** hook registry (the user chose this option over stubbing or relaxing the constraint):

- `register_turn_start_hook(f)` / `run_turn_start_hooks(project, session)` — callback registry + dispatch, with a default hook recording the last turn (`last_turn_context()`).
- `cacm_turn_start_reminder(project, session) -> Option<String>` — `async`, calls `inject()` and returns the formatted context for use as a per-turn `system_reminder`; **never fails the turn** (logs and returns `None` when the daemon is unreachable/empty).
- The binary wiring drives both at the turn boundary it owns (below).

  - **plain/json** output: `run_once`/`run_once_capture` expose no reminder parameter, so the reminder is prepended to the first user message (`with_cacm_reminder`), documented in-code.

## Notes / Follow-ups

- **`cacm_query` returns raw (unsanitized) content** — security review (sa_20260805_101005): the sanitizer only guards the `cacm.inject` formatting path; `cacm_query` hands stored content to the model as JSON tool output. It is data, not prompt text, so there is no bullet-breakout vector, but a crafted entry could still nudge the model if it treats tool output as instructions. If that is a concern, route query results through `sanitize_content` (or keep the tool advisory-only) in a follow-up.
- **Unauthenticated `cacm.context.store` + the `"*"` fallback** lets any local process poison cross-project context (sanitizer prevents breakout, not priority pollution) — pre-existing daemon design (tasks 1.2/1.4), unchanged.
- **Server/TUI path**: CACM tools and the auto-inject are available on `jcode run`/`repl`/ambient (binary-owned registries); the interactive server path needs a programmatic turn hook in `jcode-app-core` (would relax the vanilla constraint) — natural follow-up if CACM should cover interactive sessions.
- **Per-turn cost**: ndjson mode calls `inject()` once per turn (with SDK-side reconnect/backoff); plain/json modes inject once per run. If daemon latency matters, a subscription/caching layer in the SDK could serve the last-formatted context without a round-trip.
- **`CACM_DAEMON_URL`** env var overrides the default daemon address for both tools and the reminder.
